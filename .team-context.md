# Team Context - Cybereyes

## Visao Geral
- **Projeto**: Cybereyes (antes WinCare Platform, nome provisorio). Renomeacao registrada no ADR-019.
- **Objetivo**: plataforma unica de RMM + chamados para tecnicos de TI: monitoramento e gestao remota de estacoes (Windows, Linux, macOS), acesso remoto pelo navegador, chamados e incidentes, documentacao de rede, inventario de maquinas com usuarios responsaveis, logs de sistema e coleta SNMP de equipamentos de rede.
- **Base funcional**: Tactical RMM (servidor), rmmagent (agente Go), WinCare Pro (modulos de manutencao, no console: Cybereyes Care). O MeshCentral serviu de base ao acesso remoto ate a fase 12.8 e foi substituido por acesso remoto proprio (ADR-023).
- **Escala inicial**: 400 estacoes, um tecnico/equipe pequena.
- **Desenvolvimento**: Claude Code.
- **Data de inicio**: 2026-10-01
- **CTO responsavel**: CTO Skill v1

## Arquitetura
- **Padrao**: monolito modular (backend C#) + agente Go (EYES). O acesso remoto e um modulo do proprio sistema (EYES, API e console), sem servico separado (ADR-023).
- **Justificativa**: 400 estacoes cabem com folga em um unico servidor; um monolito modular entrega mais rapido, e cada modulo (RMM, chamados, inventario, documentacao, logs, SNMP) fica isolado por pasta e por schema, permitindo extrair um servico depois se for preciso.

## Stack Tecnologica
- **Backend**: C# / ASP.NET Core no .NET 10 (LTS, suporte ate 11/2028), EF Core, SignalR, Quartz.NET para jobs agendados.
- **Frontend**: React + TypeScript + Vite, TanStack Query, biblioteca de componentes (MUI ou Mantine, decidir na fase 0), xterm.js (terminal), Monaco Editor (scripts), React Flow (diagramas de rede).
- **Agente**: EYES, em Go, escrito do zero em `agent/` (Windows, Linux, macOS), com o Cybereyes Care embutido (ver ADR-007 e ADR-020).
- **App do usuario final (bandeja)**: Go + Wails v3 com interface React, para abrir chamados da propria maquina, acompanhar o andamento e conversar com o tecnico (ver ADR-008). Instalado e iniciado pelo servico do EYES no Windows e no Linux (ADR-020 e ADR-022); no macOS ainda nao.
- **Acesso remoto**: proprio, embutido no EYES e na API, com visualizador no console (ADR-023, contrato em `docs/remoto/contrato-remoto.md`). O MeshCentral saiu na fase 12.8.
- **SNMP**: biblioteca gosnmp (BSD) dentro do agente Go, em maquinas marcadas como "coletor".
- **Banco de dados**: PostgreSQL (principal, com tabelas de log particionadas por mes) + Redis (cache e backplane do SignalR).
- **Mensageria**: NATS (comunicacao servidor <-> agente, mesmo modelo do Tactical).
- **Infraestrutura**: VPS unica com Docker Compose; Nginx como proxy reverso, balanceador de carga e terminacao TLS (Let's Encrypt via Certbot ou certificado proprio); API com 2 ou mais replicas.

## Padroes de Comunicacao
- **API externa (frontend e integracoes)**: REST + OpenAPI.
- **Agente -> servidor**: REST (contrato compativel com o `apiv3` atual) + NATS.
- **Servidor -> agente**: NATS (comandos RPC por ID de agente).
- **Real-time no navegador**: SignalR (status de agentes, alertas, chamados, terminal).
- **Acesso remoto**: visualizador no console (`/acesso-remoto/:agentId`) ligado ao EYES por relay WebSocket na API (`/api/remote/relay/...`); a sessao e pedida ao EYES pelo NATS (`remote_start`).
- **App de bandeja <-> agente**: IPC local (named pipe no Windows, socket Unix no Linux e macOS).
- **App de bandeja <-> servidor**: HTTPS + SignalR com token curto emitido pelo backend a pedido do agente.

## SLAs e SLOs (ambiente de 400 estacoes, VPS unica)
- **Disponibilidade do console**: 99,5% mensal.
- **Latencia P95 da API**: < 300 ms nas telas principais.
- **Deteccao de agente offline**: < 5 min.
- **RTO**: < 2 h (restauracao de backup em nova VPS).
- **RPO**: < 24 h (backup diario do PostgreSQL e volumes; avaliar WAL continuo depois).

## Decisoes Arquiteturais (ADRs)
### ADR-001: Backend em C# / ASP.NET Core (.NET 10)
- **Status**: Aprovado
- **Contexto**: o backend atual e Python/Django; o usuario escolheu C#.
- **Decisao**: reimplementar todas as funcoes do Tactical RMM em C#, a partir de especificacao funcional.
- **Consequencias**: reescrita total do servidor; ganho de tipagem e desempenho; o contrato com o agente precisa ser mantido.

### ADR-002: Frontend em React + TypeScript
- **Status**: Aprovado
- **Contexto**: o frontend oficial do Tactical esta em outro repositorio e nao seria reaproveitado.
- **Decisao**: novo frontend React.
- **Consequencias**: todas as telas sao construidas do zero.

### ADR-003: Agente em Go, mantido no repositorio `rmmagentwincare`
- **Status**: Substituido pelo ADR-020 (agente EYES reescrito do zero em `agent/`)
- **Contexto**: o rmmagent ja funciona em Windows, Linux e macOS e e derivado de codigo sob a Tactical RMM License.
- **Decisao**: evoluir o agente Go existente; o backend C# implementa o mesmo contrato (17 endpoints `apiv3` + RPC via NATS) para o agente funcionar sem mudancas na fase 1.
- **Consequencias**: o agente fica em repositorio separado para nao misturar licencas com o repositorio privado. Ver ADR-005.

### ADR-004: Acesso remoto via MeshCentral
- **Status**: Substituido pelo ADR-023 na parte que mantem o MeshCentral (fase 12.8); o requisito de acesso remoto pelo navegador continua
- **Contexto**: o tecnico precisa de acesso remoto pelo navegador; o cliente web do RustDesk so existe na versao Pro paga.
- **Decisao**: manter o MeshCentral (Apache 2.0) como container separado, integrado pelo backend C#.
- **Consequencias**: a integracao hoje feita em Python (`meshctrl`) sera reescrita em C#. O RustDesk sai do projeto.

### ADR-005: Licencas
- **Status**: Pendente de validacao juridica
- **Contexto**: Tactical RMM e rmmagent usam a "Tactical RMM License" (nao open source; uso comercial exige autorizacao da AmidaWare; obra derivada distribuida exige codigo publico). A pasta `ee` (SSO, relatorios, white-label) tem licenca propria e nao pode ser copiada.
- **Decisao**: o backend C# e escrito a partir de especificacao funcional, sem traducao linha a linha; SSO e relatorios sao projetados do zero; nada da pasta `ee` e reaproveitado.
- **Consequencias**: reduz, mas nao elimina, o risco. A finalidade do produto (uso interno x venda/SaaS) ainda precisa ser definida com um advogado.

### ADR-006: SNMP no agente Go (papel "coletor")
- **Status**: Aprovado
- **Contexto**: usuario quer monitorar equipamentos de rede por SNMP.
- **Decisao**: uma ou mais estacoes por site recebem o papel de coletor e fazem polling SNMP v2c/v3 e recepcao de traps com a biblioteca gosnmp.
- **Consequencias**: sem servidor extra no site. A documentacao do gosnmp avisa que a recepcao de traps v3 nao e confiavel; traps v3 ficam como limite conhecido ate validacao.

### ADR-007: WinCare Pro fundido no agente Go
- **Status**: Aprovado
- **Contexto**: o WinCare Pro e uma suite PowerShell com interface WinForms, so Windows; o usuario quer que ele faca parte do agente.
- **Decisao**: os modulos do WinCare Pro viram comandos nativos do agente (`wincare_run` com modulo e parametros). Os scripts PowerShell sao embutidos no binario com `go:embed` (mesmo padrao que o agente ja usa) e o progresso volta ao console em tempo real. O Health Check (nota 0 a 100) e reescrito em Go para funcionar nos tres sistemas. A interface WinForms deixa de existir.
- **Consequencias**: um unico agente para instalar; os modulos passam a ser versionados junto com o agente.

### ADR-008: App de bandeja para o usuario final
- **Status**: Aprovado
- **Contexto**: o usuario da estacao precisa abrir chamados pela propria maquina e conversar com o tecnico atribuido.
- **Decisao**: binario `wincare-tray` no mesmo repositorio do agente, em Go + Wails v3 com interface React. O servico do agente roda como SYSTEM/root e nao consegue mostrar janelas, por isso a interface e um processo separado, iniciado em cada sessao de usuario (Windows: pelo servico na sessao do usuario; macOS: LaunchAgent; Linux: autostart XDG). Os dois sao entregues no mesmo instalador e o agente supervisiona o app.
- **Consequencias**: o chamado nasce vinculado a maquina (ID do agente) e ao usuario logado. O chat so e liberado apos a atribuicao de um tecnico. Wails v3 esta em beta (API declarada estavel pelo projeto); a versao sera fixada e o Wails v2 fica como alternativa.
